# MTG Puzzle Web — Phase 0 調査・検証手順

対象: [requiremnts.txt](requiremnts.txt) の「10. Phase 0：技術実証」と「11. 最大の技術課題」
目的: UI 開発に入る前に「Forge を外部から操作できるか」「それをブラウザで動かせるか」を判断する。

---

## 0. 前提と事前に分かっていること

| 項目 | 現状 | 影響 |
|---|---|---|
| ローカル JDK | 8 / 11 のみ | Forge 本体は **Java 17 以上** が必要 → JDK 17（または 21）を導入 |
| ビルドツール | Maven / Gradle なし | Forge は Maven プロジェクト → Maven 導入（または `mvnw`） |
| Node.js | v24 あり | Web 側（Vite + TS）はそのまま使える |
| Manabrew | 公開情報によると、ブラウザ版のエンジンは **Forge を Rust に移植したもの**（AGPL）で、Java 版 Forge は別エンジン扱い | 「Forge Java をそのまま WASM 化した実績」ではない可能性が高い。V2-A で一次情報（リポジトリ）を確認する |
| Forge のライセンス | GPL-3.0 | Web 配布時のソース公開義務を V7 で整理する |

**最初の判断点（要件より）**: ① GameState で任意盤面を復元できるか、② 外部から行動を入力できるか、③ それが WASM（ブラウザ）で動くか。
①② は JVM 上で先に確認し、③ と切り分ける。こうすれば WASM 化に失敗しても、Adapter の設計は無駄にならない。

## 1. prototype ディレクトリ構成

```
prototype/
  README.md              … セットアップ手順・検証結果のサマリ
  forge/                 … Card-Forge/forge（git submodule。コミットを固定）
  forge-adapter/         … Java: Adapter API + ヘッドレス実行ハーネス（V1, V3）
  wasm/
    teavm/               … 方式B
    cheerpj/             … 方式C
    graalvm-web-image/   … 方式D
  web/                   … Vite + TypeScript。Worker 上でエンジンを起動する最小ページ（V2, V4, V5, V6）
  puzzles/               … サンプル問題（Forge の res/puzzle/*.pzl から数問 + 独自 JSON）
  results/               … 計測結果（起動時間・メモリ・サイズ）。方式ごとに CSV/MD で残す
```

すべての方式で同じ **検証シナリオ S1〜S5** を実行し、結果を `results/` に同じ形式で記録する。

### 共通検証シナリオ

| ID | 盤面 | 操作 | 期待結果 |
|---|---|---|---|
| S1 | p1: 手札 Lightning Bolt、戦場 Mountain / p2: ライフ 3 | Mountain をタップ → Bolt を p2 に対象指定 → 解決 | p1 勝利 |
| S2 | p1: 戦場に未酔いのクリーチャー（パワー3）/ p2: ライフ 3、ブロッカーなし | 戦闘へ進む → 攻撃 → パス | p1 勝利 |
| S3 | S1 と同じ | Bolt を p1 自身に撃つ／何もせずターン終了 | 未クリア → 期限切れで失敗 |
| S4 | スタック・誘発を含む盤面（例: ETB 誘発を持つクリーチャー） | 唱える → 誘発の対象選択 → 解決 | 誘発が正しく解決される |
| S5 | S1 を進めた途中の状態 | reset | 初期盤面に完全に戻る（ID・タップ状態・ライフ） |

## 2. 検証項目と手順

### V0. 環境構築（0.5日）

1. JDK 17 か 21（Temurin）と Maven を導入する。既存の JDK 8/11 は残し、`JAVA_HOME` はプロジェクト単位で切り替える。
2. `prototype/forge` に Card-Forge/forge を submodule で追加し、**最新リリースタグに固定**する（要件「Forge 更新への追従＝バージョン固定」）。
3. `mvn -pl forge-game -am install -DskipTests` で、`forge-core` / `forge-game` だけをビルドできることを確認する。GUI モジュールは使わない。
4. 記録: ビルド時間、jar サイズ、依存ライブラリ一覧（`mvn dependency:tree`）。
   → 依存ライブラリ（Guava の EventBus、リフレクション、スレッド系）は V2 の WASM 化で問題になるため、ここで洗い出しておく。

### V1. JVM 上でのヘッドレス実行（最重要・2〜4日）

ブラウザに持っていく前に、**Forge を GUI なしで外部から操作できるか**を確認する。

1. **カード DB のロード**
   - `StaticData` / `CardDb` を、GUI に依存しない形で初期化する手順を特定する。
   - `res/cardsfolder` を全件ロードした場合と、検証シナリオで使うカードだけに絞った場合とで、時間とメモリを計測する（→ V6 のモバイル容量見積もりに使う）。
2. **Game の生成**
   - プレイヤー 2 人・空デッキで `Match` と `Game` を作る。
   - GUI の `forge-gui` が何をしているか（`HostedMatch` など）を読み、最小限の初期化手順を抜き出す。
3. **GameState による盤面復元**
   - `GameState.parse()` → `applyToGame()` で S1〜S5 の盤面を作る。
   - 確認すること: タップ状態、召喚酔い、カウンター、フェイズ、アクティブプレイヤー、マナプール、オーナー／コントローラーの区別。
   - 要件 6 章の JSON から GameState テキストへの変換を、この段階で仮実装する（`forge-adapter` 内）。
4. **外部行動入力（要件のリスク「高」）**
   - Forge では、プレイヤーの意思決定はすべて `PlayerController` を通る。次の 2 つを自作する。
     - `ExternalPlayerController`（p1 用）: 判断が必要になったら「選択要求」をキューに出し、外部からの回答を待つ。
     - `PassingPlayerController`（p2 用）: 優先権は常にパスする。強制選択には決まった方針（先頭を選ぶなど）で答え、対応できない選択が来たら例外を投げる。
   - 確認すること: `PlayerController` の抽象メソッドの数と種類（対象・モード・マナ支払い・攻撃/ブロック宣言・スカリー・順序並べ替えなど）。そのうち S1〜S4 で実際に呼ばれるのはどれか（呼び出しログを取る）。
   - **スレッドモデルの確認**: Forge のゲームループは別スレッドで動き、入力が来るまでブロックする作りになっていないかを確認する。ブロックする場合、WASM 環境（スレッドなし）では「同期的に 1 ステップずつ進める」形への改修が必要になる。これが V2 の成否を大きく左右するため、必ずここで結論を出す。
5. **勝敗・期限の検出**
   - `GameEvent` を購読して、勝敗確定・ターン/フェイズ遷移・異常終了を拾えるか確認する（要件 5 章「期限の境界は Forge のイベントで判定」）。
   - あわせて `Puzzle.addGoalEnforcement()` の実装も読み、流用できる部分を判断する。
6. **リセット**
   - 同じ JSON から Game を作り直す方式と、`initFromGame()` でスナップショットを取る方式とを比べ、所要時間を測る。

**V1 の合格条件**: S1〜S5 が JUnit などのテストとして JVM 上で自動実行でき、p1 の操作をすべて「選択要求 → 回答」の形で外部から与えられること。

### V2. WASM／ブラウザ実行方式の比較（3〜5日）

V1 のハーネス（GUI なし・`forge-adapter` を含む jar）を、そのまま各方式に載せて S1 を実行する。

| 方式 | 内容 | 主な確認点 |
|---|---|---|
| A. Manabrew 再利用 | 一次情報（リポジトリ・ライセンス）を確認する | Java 版 Forge の WASM 化か、Rust 移植か。AGPL と本プロジェクトの関係。カードの網羅率。API を外部から呼べるか |
| B. TeaVM | Java バイトコードを JS/WASM に変換 | リフレクション、`java.io` によるファイル読み込み、スレッド、Guava が動くか |
| C. CheerpJ | ブラウザ上で JVM バイトコードを実行 | 起動時間、ダウンロードサイズ、商用利用時のライセンス条件 |
| D. GraalVM Web Image | GraalVM の WASM 出力（実験的機能） | 対応 JDK と成熟度、リフレクション設定、出力サイズ |

各方式で記録すること:
- ビルドの可否と、そのために必要だった Forge 側の改修（差分の行数）
- 初回ロードのサイズ（gzip / brotli 後）と、初期化完了までの時間
- S1〜S5 が通るか
- Web Worker 上で動くか。動かすのに COOP/COEP（`SharedArrayBuffer`）が必要か
- 1 アクションあたりの応答時間

カードデータは全件を同梱せず、「問題で使うカードだけを動的に読み込む」方式が使えるかも、ここで確認する。

**V2 の合格条件**: 少なくとも 1 方式で、PC ブラウザ上で S1〜S5 が通り、初期化が実用的な時間（目安 10 秒以内）で終わること。

### V3. Adapter API の確定（1〜2日）

V1・V2 の結果をもとに、TypeScript から見えるインターフェースを固める。最小構成の案:

```ts
interface ForgeEngine {
  load(puzzle: PuzzleJson): LoadResult;          // 不正な盤面ならエラー詳細を返す
  getState(): GameView;                          // UI 表示用。Forge の内部構造は露出しない
  getPendingDecision(): Decision | null;         // 対象選択・支払いなどの選択要求
  getActions(): Action[];                        // 唱える/起動/パス 等の合法手
  submit(input: Action | DecisionAnswer): StepResult;  // 返り値にイベント列を含める
  reset(): void;
}
```

- Worker 越しに使うため、やり取りはすべてシリアライズ可能な JSON にする。
- インスタンス ID（要件 6 章の `c1` など）と Forge の内部カード ID との対応表は Adapter が持つ。

### V4. パズル判定（0.5〜1日）

- `submit()` が返すイベント列から `PuzzleGoal{type:"win", deadline:"current_turn"}` を判定する純粋な TS 関数を作り、S1〜S3 で「クリア／期限切れ失敗／敗北失敗」を確認する。
- 異常終了（例外・未対応の選択）が起きたときに、クリア扱いにならないことも確認する。

### V5. URL 共有（0.5日）

- JSON を圧縮（`CompressionStream('deflate-raw')` と lz-string を比較）し、base64url にしてフラグメントへ格納 → 復元、の往復で同一性を確認する。
- 盤面の規模を小・中・大（カード 5 / 20 / 60 枚）で変えて URL 長を計測する。目安として、SNS・チャットで共有して壊れにくい 2,000 文字以内に収まるかを見る。
- Phase 0 で必須の項目ではないので、他の作業と並行して進めてよい。

### V6. スマートフォン実機での計測（1日）

- V2 で合格した方式を、iOS Safari と Android Chrome の実機で開く（Cloudflare Pages のプレビュー、または LAN 内の開発サーバー経由）。
- 計測すること: 初期化時間、メモリ使用量（Safari の Web Inspector / Chrome のリモートデバッグ）、タブがクラッシュしないか、バックグラウンドから戻ったときの挙動。
- COOP/COEP が必要な方式の場合は、Cloudflare Pages の `_headers` で設定して動作を確認する。

### V7. ライセンスとカード画像（並行・調査のみ）

- Forge（GPL-3.0）を WASM にして配布する場合の義務を整理する（ソースの公開方法、改変部分の扱い）。
- 方式 A（AGPL）、方式 C（CheerpJ）を採る場合は、それぞれのライセンス条件を確認する。
- カード画像・テキストの取得元（Scryfall など）の利用規約と、WotC の Fan Content Policy との関係を確認する。
- 本番公開前に、法務への相談が必要かどうかを判断する。

## 3. 判断ゲート

| ゲート | タイミング | 判断 | 不合格だった場合 |
|---|---|---|---|
| G1 | V1 完了 | 外部入力とパス専用コントローラーが成立するか | Forge 改修の規模を見積もり直す。大きすぎる場合は、Forge 以外のエンジンも検討する |
| G2 | V2 完了 | ブラウザで動く方式があるか、どれを採るか | 「バックエンド不要」の前提を見直す（サーバーで Forge を動かす構成の検討） |
| G3 | V6 完了 | スマホで実用に耐えるか | カードデータの削減や遅延ロードを検討する。またはスマホを当面「閲覧のみ」とする |

G1・G2 を通過するまでは、Web UI（エディタ・盤面表示）の作り込みに着手しない。
