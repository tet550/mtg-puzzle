MTG Puzzle Web 設計

1. プロジェクト概要
ForgeのMTGルールエンジンをWebAssembly（WASM）でブラウザ上に実行し、任意の盤面からプレイできるMTGパズルサービスを構築する。
ユーザーは盤面を自由に作成し、URLで共有できる。共有された問題を開いたプレイヤーは、MTGのルールに従ってカードを操作し、指定された条件を達成するとクリアになる。
基本コンセプトは 「MTGの詰将棋を作成・共有・プレイできるWebサイト」。
基本仕様
項目	方針
プラットフォーム	静的Webサイト
PC対応	必須
スマートフォン対応	必須
バックエンド	不要
ゲームルール	Forge
実行方式	WebAssembly
盤面復元	Forge GameState
パズル機能	独自実装
UI	独自Web UI
問題データ	JSON
問題共有	URL
対戦AI	MVPでは不要
LLM	使用しない
アカウント	不要
2. 全体アーキテクチャ
Web Application（TypeScript）
盤面エディタ・パズルプレイヤー・共有UI

Puzzle Core（TypeScript）
問題データ・URL変換・クリア条件・進行状態

Forge Adapter（TypeScript / Java）
初期盤面構築・状態取得・行動入力・イベント変換

Forge WASM
GameState・Game・カード効果・スタック・戦闘・勝敗


コンポーネントの責務
コンポーネント	主な責務
Web UI	カード表示、盤面操作、問題作成
Puzzle Core	問題定義、URL共有、クリア判定
Forge Adapter	Forgeとのデータ・操作の受け渡し
Forge GameState	指定された盤面の構築・復元
Forge Game	ルール処理、カード効果、ターン進行
Forgeのルール処理をTypeScript側で再実装しないことを基本原則とする。
3. Forgeの利用範囲
調査した既存ソースを基に、再利用する範囲を明確にする。
Forgeの機能	採用方針
Game	利用
GameState.parse()	利用
GameState.applyToGame()	利用
GameState.initFromGame()	必要に応じて利用
カード定義・効果処理	利用
合法手・マナ・戦闘・スタック処理	利用
Puzzle.java	参考実装として利用
Puzzle.addGoalEnforcement()	必要に応じて処理方式を流用
PuzzleIO	不採用
デスクトップのPuzzle作成UI	不採用
Forge AI	MVPでは不採用
Forge本体への変更は可能な限り小さくし、必要な機能をAdapterとして追加する。
4. 機能設計
4.1 問題作成モード
ユーザーはGUI上で自由に初期局面を設定する。
MVP対象
- カードの検索・追加・削除
- 手札、戦場、墓地、追放領域へのカード配置
- プレイヤーのライフ設定
- タップ状態、召喚酔い、カウンターの設定
- 初期マナプール設定
- アクティブプレイヤー、フェイズの設定
- 勝利条件、ターン制限の設定
- 問題のテストプレイ
- URL生成とコピー
後続対応
- ライブラリー順序の詳細設定
- 装備・オーラ等のアタッチ
- スタックに積まれた状態からの開始
- 対戦中の盤面を問題として保存
- 解答手順の記録
4.2 パズルプレイモード
共有URLから問題を読み込み、Forge上に盤面を復元する。
通常のMTG対戦と同じルールで以下を操作できる。
- 呪文を唱える
- 能力を起動する
- マナを支払う
- 対象・モードを選ぶ
- 優先権をパスする
- 攻撃・ブロックを処理する
- ターンを進める
問題終了時にはクリア・失敗を表示する。
問題の初期状態へのリセットは必須とし、任意時点へのUndoは後続機能とする。
4.3 相手プレイヤーの扱い
MVPでは対戦AIを利用しない。
基本方針は、相手は任意の呪文・能力を使用せず、自動で優先権をパスすること。
強制選択が発生する場合は、問題で定めた方針を利用する。対応できない選択が発生する問題は、作成時の検証で検出する。
将来的には、相手の行動をスクリプトとして定義する機能を追加できる設計にする。
5. パズルのクリア判定
Forgeの既存Puzzle Modeは、統率領域に特殊な「Puzzle Goal」を生成して条件を処理している。
Web版では、原則としてゲーム状態を監視する独立したパズル判定機構を採用する。
MVPの条件
type PuzzleGoal = {
  type: "win";
  player: "p1";
  deadline: "current_turn";
};


判定方針：
- Forgeが対象プレイヤーの勝利を確定したらクリア
- 指定された期限を超えたら失敗
- 対象プレイヤーが敗北したら失敗
- ゲームが異常終了した場合はクリア扱いにしない
期限の境界は、Forge側のゲームイベントに基づいて判定する。
将来の条件
条件	例
勝利	このターン中に勝利
生存	次の相手ターンまで生存
除去	特定のパーマネントをすべて除去
展開	指定クリーチャーを戦場に出す
制限	3回以内の呪文で勝利
禁止	指定カードを使用せず勝利
6. 問題データ設計
Web側ではForge内部のテキストフォーマットを直接使わず、バージョン付きJSONで管理する。
{
  "schemaVersion": 1,
  "title": "Lethal Puzzle #001",
  "description": "Win this turn",
  "engine": {
    "type": "forge",
    "version": "pinned-version"
  },
  "game": {
    "activePlayer": "p1",
    "phase": "main1",
    "players": [
      {
        "id": "p1",
        "life": 5,
        "hand": [
          {
            "id": "c1",
            "cardId": "lightning-bolt"
          }
        ],
        "battlefield": [
          {
            "id": "c2",
            "cardId": "mountain",
            "tapped": false
          }
        ]
      },
      {
        "id": "p2",
        "life": 3,
        "battlefield": []
      }
    ]
  },
  "goal": {
    "type": "win",
    "player": "p1",
    "deadline": "current_turn"
  },
  "opponent": {
    "policy": "pass"
  }
}


上記は独自スキーマの構造例。カードIDと内部データの実際のマッピングは別途定義する。
データ設計の原則
- Forgeの内部オブジェクト構造には依存させない
- 同名カードを個別に識別するインスタンスIDを持つ
- カードの所有者とコントローラーを区別する
- 不正なゲーム状態を検出する
- 問題データの形式とForgeバージョンを管理する
- 互換性がない古い問題には適切なエラーを表示する
Forgeの .pzl 形式からのインポートは、将来の互換機能として実装する。
7. URL共有
問題データをJSONから圧縮・URL安全な文字列に変換し、URLのフラグメント部分に格納する。
https://example.com/#p=<compressed-puzzle>


基本動作
1. 問題作成者が盤面を設定する。
2. 問題データを検証する。
3. JSONを圧縮してURLへ変換する。
4. URLをコピーして共有する。
5. 受信者が開くと自動で盤面が復元される。
静的ホスティングだけで成立させるため、MVPではサーバーへの保存を不要とする。
ただし、大きな問題データはURL長制限に抵触する可能性があるため、圧縮後の長さを検証する。
8. UI設計
PCとスマートフォンで、同じゲームモデルを使用する。
PC
- 相手の戦場：画面上部
- 自分の戦場：中央
- 手札：画面下部
- カード詳細：右側パネル
- 問題目標・操作履歴：サイドパネル
スマートフォン
- 盤面を縦方向に表示
- 手札は横スクロールまたは展開式
- カード長押しで詳細表示
- タップでカード選択
- 利用可能アクションをメニューで表示
- 対象指定・マナ支払いは段階的に操作
スマホではカードのドラッグ＆ドロップを必須とせず、タップ操作を基本とする。
9. 実行環境
項目	方針
言語	TypeScript / Java
Web UI	TypeScriptベース
ルールエンジン	Forge WASM
スレッド	可能ならWeb Worker
保存	URL、必要に応じてIndexedDB
ホスティング	Cloudflare Pages等
通信	初期リソース取得・カード画像取得のみ
サーバー処理	なし
WASMのスレッドや共有メモリを利用する場合、必要なCOOP/COEP等のヘッダーに対応したホスティングを採用する。
なお、ManabrewによるForge WASM化の実績はあるものの、その成果物を本プロジェクトに再利用できるかは未確定。自前ビルドも選択肢として残す。
10. 開発フェーズ
1. Phase 0：技術実証（最優先）
   Forge WASMの取得またはビルドを行い、ブラウザから次の操作が可能であることを確認する。
   - 指定盤面のロード
   - ゲーム状態の取得
   - 呪文の実行と効果解決
   - 勝敗判定
   - ゲームの再初期化
   PCとスマートフォンの双方で動作確認する。
2. Phase 1：パズルプレイヤー
   既存の .pzl などから固定のサンプル問題をロードし、実際に操作してクリアできる状態を作る。
3. Phase 2：盤面エディタ
   カードの検索、配置、状態設定、初期盤面の検証、テストプレイを実装する。
4. Phase 3：URL共有
   問題データの圧縮、URL生成、別端末での復元を実装する。
5. Phase 4：公開品質への改善
   スマホUI、エラー処理、キャッシュ、バージョン互換性、サンプル問題、ライセンス対応を完成させる。
11. 最大の技術課題
課題	リスク	対策
ForgeのWASM化	高	既存実装を調査し、小規模PoCで確認
Forgeへの外部行動入力	高	Java側に最小APIを追加
任意の盤面復元	中	GameStateを利用し、対象状態を制限
相手の自動パス	中	専用コントローラーで制御
モバイルメモリ	中〜高	実機計測、読み込む資産の削減
URLの長さ	低〜中	JSON圧縮、サイズ制限
Forge更新への追従	中	バージョン固定、Adapter分離
ライセンス・画像利用	中〜高	GPL条件とカード画像の利用条件確認
12. MVP完成条件
以下をすべて満たした状態をMVPとする。
- PCとスマートフォンのブラウザで問題を開ける
- サーバーを介さずForgeがルール処理を実行する
- 任意のカードを配置した初期盤面を作成できる
- 呪文・能力・戦闘などをルール通り処理できる
- 今ターン中の勝利を自動判定できる
- URLで問題を共有できる
- 他の端末でも同じ初期盤面を再現できる
- 初期状態にリセットして再挑戦できる
- 問題が不正な場合にエラーを表示できる

最終的な設計方針
ForgeはMTGルールとゲーム状態のエンジンとして使い、パズルという製品機能は独立して実装する。
この境界を維持することで、将来は同じ基盤から次の機能へ拡張できます。
- 一人回し
- コンボ検証
- 盤面共有
- プレイ手順の比較
- リーサル問題の投稿
- 問題集・ランキング
- AIによる問題生成や解法探索
特に重要なのは、パズル専用アプリを作るのではなく、任意のMTG盤面を再現・操作できるWeb基盤に、パズル機能を載せるというアーキテクチャです。
実装面では、GameStateの再利用とForge WASMの外部制御APIが成立するかが最初の判断点になります。ここをクリアしてからUI開発に進むことで、大きな手戻りを避けられます。
