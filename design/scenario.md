# シナリオ（解答手順）で問題を確かめる

ソルバー（`Solver.java`、選択肢の総当たり）をやめて、問題の作者が書いた解答手順（シナリオ）で「この問題は Adapter で解ける」ことを確かめる。

## 1. なぜ変えるか

| 問題点 | 内容 |
|---|---|
| 探索が実用にならない | 分岐を減らす決まり（マナは常に自動、攻撃は全員かなし、組み合わせは 20 通りまで）があっても、手数の多い問題（S11 など）は時間内に解けない。マナ能力を優先権で起動できるようにすると、土地の数だけ分岐が増える |
| 解答が位置で書かれている | `*.solution.json` は選択肢の位置（`indexes`）で手を持つ。選択肢の並びが変わると、別の手を指したり範囲外になったりする（マナ能力を優先権の選択肢に加えた変更で並びが変わる） |
| 人が書けない | 位置は実際に選択肢を出してみないと分からない。ラベルは長い英語の文で、手で書き写すのは難しい |

## 2. シナリオの形式

`app/public/puzzles/<問題 ID>.scenario.json`（`*.solution.json` を置き換える）。

```json
{
  "puzzle": "s1-bolt",
  "steps": [
    { "kind": "PRIORITY", "pick": { "card": "c2", "ability": "mana" } },
    { "kind": "PRIORITY", "pick": { "card": "c1", "ability": "spell" } },
    { "kind": "TARGETS",  "pick": "p2" },
    { "kind": "PRIORITY", "pick": "pass" }
  ]
}
```

- 1 つの手が 1 つの選択要求（Decision）への回答に当たる。`kind` は確かめるために書く（違えば失敗にする）。
- `pick` は選ぶ選択肢。複数を選ぶ選択要求では配列にする（`[]` で 0 個）。
- `{ "repeat": 7, "steps": [ ... ] }` で、同じ手の並びを繰り返す（S11 のループ）。

### 選択肢の指し方（セレクター）

選択肢の位置や ID は使わない。問題データの ID と、能力の種類・文の一部で指す。

| 書き方 | 当たる選択肢 |
|---|---|
| `"pass"` / `"auto"` / `"cancel"` / `"yes"` / `"no"` | `ref.type = special` で値が同じもの |
| `"p1"` / `"p2"` | そのプレイヤー |
| それ以外の文字列（`"c1"`、`"h3"`） | そのカード（`ref.cardId`）を指す選択肢。カードそのものでも、そのカードの能力でもよい |
| `{ "card": "c1", "ability": "activated", "text": "{5}" }` | 条件をすべて満たすもの。`ability` は spell / activated / mana / land、`text` はラベル（英語）に含まれる文 |
| `{ "text": "3" }` | ラベルに含まれる文で指す（モード・数・色など、盤面に無いもの）。`"exact": true` で完全一致 |

- **ちょうど 1 つに当たらなければ失敗**にする（無い・2 つ以上ある）。失敗のときは、選択肢の一覧を出して直しやすくする。曖昧なまま先頭を選ぶと、位置で書いていたときと同じ壊れ方をするため。
- カードの ID は問題データの ID（インスタンス ID）。リセットしても変わらない。途中で作られたトークンには問題データの ID が無い（`f<Forge の ID>`）。トークンを指すときは `text` で指す。

### 終わりの条件

- 最後の手のあとに `CLEARED` になっていること。
- 既定の答え（`fallback`）を使っていないこと（Adapter が未対応の選択を含む解答は、解けたとみなさない。今のソルバーと同じ）。

## 3. どこで使うか

| 場所 | 内容 |
|---|---|
| JVM の確かめ（`tools/build-engine.sh`） | `Solver --verify` の代わりに `ScenarioRunner`。縮めた jar と、問題ごとに抜き出したカードデータで、WebApi を通して解き直す（ブラウザと同じ流れ） |
| JUnit（`mvn test`） | `app/public/puzzles/*.scenario.json` をすべて ForgeSession で解き直す。jar を作らずに、Adapter を変えたときにすぐ確かめられる |
| E2E（`app/e2e/solve.spec.ts`） | シナリオどおりに画面のカード・ボタンを押して解く。セレクターから選択肢を決め、その選択肢を画面で押す |

セレクターの照合は、Java（`ScenarioRunner`）と TypeScript（`app/src/engine/scenario.ts`、E2E から使う）の 2 か所に置く。照合の決まりは上の表だけに限り、両方に同じテストケースを持たせる。

## 4. シナリオの作り方

1. **手で書く**。問題の作者は解き方を知っているので、上の書き方で書く。カードの ID は問題データにある。
2. **画面で解いて書き出す**（次の段階）。開発用の画面で問題を解くと、選んだ選択肢からセレクターを作り、シナリオとして保存できるようにする。選んだ選択肢の `ref` から作る（special → 値、player → ID、カード → ID、能力 → `{card, ability}`、同じカードに同じ種類の能力が 2 つ以上あれば `text` を足す、`ref` の無いもの → `{text, exact}`）。書き出したものを手で読みやすく直す（`repeat` にまとめるなど）。
3. 既存の `*.solution.json` は、ラベルで選択肢を引き当てて 2. と同じ方法でセレクターに変換する（1 回だけ）。

## 5. 相手の選択と、決めていないこと

- 相手（p2）はパスとブロックの決まり（`BlockPlanner`）しか持たないので、シナリオは 1 本道でよい。Possibility Storm の問題のように「相手のどの選択にも勝てること」が条件の問題は、今は確かめられない。相手の選択に分岐を持たせる（`opponent.block` を変えた複数のシナリオを置く、など）のは、相手の選択を Adapter が問い合わせられるようになってから決める。
- シナリオは「解ける」ことだけを確かめる。別の解き方があるか、意図しない近道が無いかは確かめない（ソルバーも実際には確かめられていなかった）。
- 「ヒントを見る・答えを見る」機能にシナリオを使うかどうかは、Phase 2 で決める。
