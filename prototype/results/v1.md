# V1 結果（2026-10-19）— JVM 上でのヘッドレス実行

## 結論（G1 判定材料）

**JVM 上では成立した。** forge-gui（GUI 層）を使わず、Forge 本体も改修せずに、次のことができた。

- JSON の問題データから盤面を復元する
- p1 の判断（優先権・対象・攻撃宣言・任意誘発）を外部から「選択要求 → 回答」の形で与える
- 相手（p2）は自動でパスする
- 勝敗と期限を判定する
- 初期盤面にリセットする

ただし、以下の 3 点は **WASM 化（V2）とモバイル対応の前に方針を決める必要がある**。
1. **スレッド依存**: 外部入力はゲームスレッドをブロックして待つ方式で実現している。
2. **forge-ai への依存**: マナ・コストの支払いと、未対応の選択を AI に任せている。
3. **初期化時間**: 約 4〜5 秒かかる。

## 実装（`prototype/forge-adapter`）

| クラス | 役割 |
|---|---|
| `ForgeRuntime` | forge-gui の `FModel` を使わずに、`StaticData`・型リスト・言語・AI プロファイルを初期化する |
| `PuzzleDefinition` | 問題データ JSON（要件 6 章のサブセット）。Forge の GameState テキストに変換する |
| `ForgeSession` | Adapter API。`load` / `getPendingDecision` / `submit` / `getState` / `reset` を提供し、勝敗・期限を判定する |
| `ExternalPlayerController` | p1 用。優先権・対象・攻撃宣言・任意誘発の確認を外部に問い合わせる |
| `PassingPlayerController` | p2 用。常にパスし、攻撃もブロックもしない |
| `DecisionChannel` | ゲームスレッドと呼び出し側との間で、選択要求と回答を受け渡す |

Forge は `Match.startGame(game, hook)` に `GameType.Puzzle`（マリガンなし）と開始手札 0 枚を指定し、hook の中で `GameState.applyToGame` を呼ぶ。デスクトップ版のパズルモードと同じ手順。

| 項目 | 遅延ロード | 全件ロード |
|---|---|---|
| `ForgeRuntime.init` | 4.8 秒 | 3.8 秒 |
| 初期化後のヒープ使用量 | **54 MB** | 146 MB |
| `load` から最初の選択要求まで | 約 20 ms | — |
| 1 ステップ（submit 1 回） | 1〜70 ms | — |
| `reset` | 15〜23 ms | — |

- 遅延ロードでもメモリは約 1/3 で済む。一方、時間はむしろ遅い。全件ロードはスレッドプールで並列に読むので速くなる。遅延ロードでも 34k ファイルの列挙と 681 件の editions の解析が残るので、初期化時間の内訳は V2 で分析する。
- リセットはゲームを作り直す方式で十分に速い（`initFromGame` によるスナップショットは不要）。

## 分かったこと・落とし穴

1. **型リストの読み込みが必須**: `res/lists/TypeLists.txt` を読まないと、基本土地タイプが認識されない。その結果 Mountain がマナ能力を持たず、**エラーも出ないまま**呪文が唱えられなくなる。この処理は forge-gui の `FModel.loadDynamicGamedata()` の中にあるため、Adapter 側に移植した。WASM 版でも同様に、forge-gui が暗黙に行っている初期化を漏れなく拾う必要がある。
2. **画像キャッシュの設定が必須**: カードを生成するときに `ImageKeys` が参照されるため、ダミーのディレクトリ設定が必要だった（実際には読まない）。
3. **存在しないカードは無視される**: `GameState` は存在しないカード名を標準エラーに出すだけで読み飛ばす。そのため Adapter 側で事前に検証している（S7）。
4. **インスタンス ID との対応**: `GameState` の `Id:` は Forge 内部の参照用でしかない。そこで、ゾーン内の並び順とカード名を照合して、問題のインスタンス ID と Forge のカード ID を対応付けた。順序がずれた場合はエラーにする。
5. **スレッドモデル**: `GameAction.invoke()` は、スレッド名が `Game` で始まるときだけ同期実行される。そうでなければスレッドプールに投げる。ゲームループ（`mainGameLoop`）は `PlayerController` を同期的に呼ぶので、外部入力を待つにはゲームスレッドをブロックするしかない。
   - JVM・CheerpJ・TeaVM（JS 出力で、スレッドをコルーチンとして扱う機能あり）ならこのままで動く見込み。
   - スレッドのない WASM（GraalVM Web Image や TeaVM の WASM 出力など）では、別の方式が要る。案は「回答ログを持ってゲームを最初から再実行する（リプレイ方式）」か、「`mainLoopStep()` を 1 ステップずつ回し、入力待ちを例外で抜ける」か。`DecisionChannel` は回答ログを記録しているので、リプレイ方式は実装しやすい。ただし決定性（乱数シード）の検証が必要。
6. **forge-ai への依存**: マナ支払い（`ComputerUtilMana`）とコスト支払い（`AiCostDecision`）を AI のロジックに任せている。forge-gui にある人間用の実装（`HumanPlay` / `InputPayMana`）は GUI と強く結びついている。「マナ支払いを段階的に操作する」（要件 8 章）を実現するには、どちらかを Adapter 向けに移植する必要がある。
7. **相手の強制選択**: `PassingPlayerController` は PoC では AI に任せている。本番では「問題で定めた方針」で答え、対応できない選択は作成時に検出する（要件 4.3）。fallbackLog はその検出に使える。

## G1 判定案

**合格（条件付き）**。V2 では次の 3 点を確認対象に加える。
- ゲームスレッドをブロックする方式が、各 WASM 方式で動くか（動かない方式ではリプレイ方式を試す）
- forge-ai 込み（jar 1 MB）でのサイズと初期化時間
- 初期化時間の内訳（editions・cardsfolder の列挙）と、事前にシリアライズして短縮できるか

## 未対応（V1 では扱っていない）

- マナを手動で支払う（どの土地をタップするかを選ぶ）
- モード選択・X の値・追加コスト・代替コストの外部入力（現状は AI が代行し、記録だけしている）
- 同時に誘発した能力の順序指定
- リプレイ方式で決定的に再現できるかの検証
