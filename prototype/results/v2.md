# V2 結果（2026-10-19）— WASM／ブラウザ実行方式の比較

## まとめ

| 方式 | 結果 | 一言 |
|---|---|---|
| A. Manabrew 再利用 | ❌ 対象外 | ブラウザ版は Rust で移植した独自エンジン。Java 版 Forge はサーバー側（GraalVM native-image）で動かしている |
| B. TeaVM 0.16.0 | ❌ そのままでは変換できない | 未対応の JDK API が 56 種類。並行処理・ロギング・Guava キャッシュ・リフレクションなど |
| C. CheerpJ 4.3（Java 17 プレビュー） | ✅ **ブラウザ上で S1〜S8 が JVM と同じ結果** | Forge は無改修で動く。ただし外部 CDN への依存とライセンスが課題 |
| D. GraalVM Web Image | ⏭ 今回は見送り | 実験的機能で、スレッドが使えない見込み。必要になったら再検討する |

**G2 判定の暫定案**: 「ブラウザで動く方式がある」は **CheerpJ で成立**。ただし本番採用には、ライセンス・外部 CDN・起動時間の 3 点を解決する必要がある。D は今回見送った。

---

## 共通の準備

- **Adapter API の JSON 化**（`WebApi`）: `init(zip, dir)` / `load(json)` / `submit(idsJson)` / `reset()` / `state()`。どの方式でも、JS との境界を文字列だけにする。
- **res のミニバンドル**（`ResBundler`）: 問題で使うカードだけを入れた cardsfolder に、editions・tokenscripts・型リストなどを加えた zip。**2.2 MB / 1,622 ファイル**。
  - Forge の遅延ロードは、索引を作るために cardsfolder の **全 34k ファイルを読む**。ブラウザでは使えないので、ビルド時に絞り込む方式にした。
  - JVM での初期化はミニバンドルで **0.9 秒**（全件読み込みは 3.8〜4.8 秒）。
- **依存込み jar**（`forge-adapter-all.jar`）: **16 MB**（圧縮後のクラスは約 12 MB）。大きいのは commons（2.5 MB）、Guava（2.4 MB）、forge-game（2.3 MB）、Jackson（1.9 MB）、forge-ai（1.0 MB）、jgrapht（0.9 MB）。
- **検証ページ**: `web/common/harness.js`（全方式で共通の最小 UI と、自動操作用の `__harness.play`）と、`web/serve.mjs`（Range 対応の静的サーバー。COOP/COEP の付与は任意）。

## A. Manabrew

- 一次情報（GitHub の witchesofthehill/manabrew）によると、ブラウザの WASM で動いているのは **Rust で書かれたエンジン**（`manabrew-rs/crates/wasm`）。カードの網羅率は「一部の対戦のみ」。
- Java 版 Forge は **GraalVM native-image で共有ライブラリにして**、サーバーやデスクトップ側で動かしている（`forge-harness/native`）。
- ライセンスは AGPL-3.0（Forge 由来の部分は GPL-3.0）。
- 結論: 「Java 版 Forge をブラウザで動かす」成果物としては再利用できない。ただし、**Forge を native-image に通すためのリフレクション設定**は、方式 D の参考になる。

## B. TeaVM 0.16.0（JS 出力）

`wasm/teavm` で `WebApi` 全体を到達可能にしてビルドすると、**133 件のエラー（未対応 API は 56 種類）**が出て、出力は空だった。詳細は [v2-teavm-build.log](v2-teavm-build.log)。

| 分類 | 主な API | 発生元 |
|---|---|---|
| 並行処理 | `ReentrantLock`, `ReadWriteLock`, `Executors`, `LinkedBlockingQueue`, `ConcurrentSkipListMap`, `FutureTask` | Forge（`ThreadUtil`, `Game`, `Match`）、Guava の `LocalCache`、Adapter の `DecisionChannel` |
| ロギング・監視 | `ManagementFactory`, `ProcessHandle`, `java.sql`, `javax.naming`, `URLClassLoader` | tinylog、sentry |
| リフレクション | `Class.getGenericSuperclass`, `getGenericInterfaces`, `Constructor.canAccess` | Jackson、Forge（`TriggerType` など） |
| ファイル | `File.toPath`, `RandomAccessFile.getChannel`, `FileLock` | Forge の `CardStorageReader` / `FileUtil`、tinylog |
| その他 | `Normalizer.Form.NFKD`, `UUID` のビット取得, `Date.toInstant` | Forge、sentry |

- ビルド時に見つからないものとは別に、実行時にだけ表に出る問題もある。Guava の `EventBus`（`@Subscribe` をリフレクションで呼ぶ）と、`TriggerType` / `ReplacementType` のコンストラクタ呼び出しは、ビルドを通しても実行時に動かない可能性が高い。
- 対応するとすれば、(1) tinylog / sentry をスタブに置き換える、(2) 並行処理 API を TeaVM のクラスライブラリで補う（グリーンスレッドの上でロックや Executor を実装する）、(3) Jackson を外して、JSON の受け渡しを JS 側か手書きのシリアライザで行う、(4) EventBus とリフレクションによる生成を明示的な登録に置き換える（Forge の改修）。**Forge 本体への改修が数か所〜数十か所**になる見込みで、「Forge の改修は最小限」という方針と衝突する。

## C. CheerpJ 4.3（`cheerpjInit({version: 17})`）

`web/cheerpj/index.html`。`forge-adapter-all.jar` を **そのまま** `cheerpjRunLibrary` で読み込み、`WebApi` を JS から呼んだ。

### 動作結果（ブラウザ）

| シナリオ | 結果 |
|---|---|
| S1 Bolt | ✅ CLEARED |
| S2 攻撃 | ✅ CLEARED |
| S3b 自分に Bolt | ✅ FAILED（敗北） |
| S4 ETB 誘発の対象指定 | ✅ Grizzly Bears が墓地へ |
| S5 リセット | ✅ 初期盤面に戻り、再度クリアできた |
| S6 起動型能力 | ✅ CLEARED |
| S8 パスし続ける | ✅ FAILED（期限切れ） |

ゲームスレッドをブロックする方式（`DecisionChannel` の BlockingQueue）も、そのまま動いた。CheerpJ は Java のスレッドに対応している。

### 計測（アプリ内ブラウザ、ペイン表示中、localhost）

| 項目 | 時間 |
|---|---|
| `cheerpjInit` + `cheerpjRunLibrary`（boot） | 2.3 秒 |
| res-mini.zip を /files（IndexedDB）に展開 | 4.5 秒（1,622 ファイル） |
| `ForgeRuntime.init` | 3.8 秒（JVM では 0.9 秒） |
| **準備完了まで合計** | **10.7 秒** |
| `load`（パズルの読み込み） | 0.2〜0.4 秒 |
| `submit` 1 回 | 約 40 ms |
| `reset` | 約 60 ms |

- ペインが非表示（バックグラウンドのタブ）の間は、boot に 111 秒、展開に 40 秒かかった。計測は必ず表示状態で行う。
- 展開済みなら展開を省くキャッシュは実装した（`.bundle-size` マーカー）。ただし下の問題のため、2 回目以降の読み込み時間は未計測。

### 問題点

1. **record のリフレクションが未実装**: コンソールに `TODO: JVM_IsRecord` が出て、Jackson が record を `{}` としてシリアライズした。そこで `WebApi` で明示的に Map に変換して回避した。Forge 内部の record は、リフレクションを使わない限り問題ない。Java 17 対応はまだプレビューなので、ほかにも穴がある可能性がある。
2. **外部 CDN への依存**: ランタイムは `cjrtnc.leaningtech.com` から読み込む。このアプリ内ブラウザでは同ドメインが **組織ポリシーでブロックされており**、初回はサブリソースとして読めたものの、2 回目以降は内部の iframe（c.html）が開けず（origin が `null`）、初期化が止まった。社内ネットワークや企業環境の端末では動かない可能性がある。自前でホスティングするには商用ライセンスが必要。
3. **ライセンス**: CheerpJ Core の無償版（Community Edition）は「個人プロジェクト、FOSS、技術評価」向け。商用（会社としての提供）では、Small Business ライセンス（10 人まで、開発者 1 人あたり月 £100）か Enterprise ライセンスが必要で、**アプリ単位で課金**される。本プロジェクトを GPL の FOSS として公開するなら無償の範囲に入る可能性があるが、要確認。
4. **起動時間**: 10 秒台はパズルを開くたびに待つ時間としては長い。改善の余地は (a) jar の縮小（Jackson を外す、ProGuard で未使用クラスを削る）、(b) editions の絞り込み、(c) 展開をやめて `/str/` か `/app/` から直接読む、(d) CheerpJ の preloadResources 機能。

## D. GraalVM Web Image（今回は見送り）

今回の V2 では試さなかった。CheerpJ の課題（ライセンス・CDN・起動時間）が解決できない場合の代替候補として、以下の情報を残しておく。


- 必要なもの: Oracle GraalVM 25.1 以上（現行は 25.4 Innovation。Windows x64 の zip は 371 MB、GFTC ライセンス）と、Binaryen 119 以上（現行は version_133）。
- 公式ドキュメントでは「実験的」扱い。WebAssembly の GC・例外処理・型付き関数参照を使う。
- 公式ドキュメントにスレッドへの言及はなく、コミュニティの報告では **マルチスレッドは使えない**。その場合、現在のゲームスレッドをブロックする方式は動かない。V1 の結果に書いた「リプレイ方式」か「ステップ実行方式」への切り替えが必要になる。
- リフレクションは、到達可能性メタデータ（reflect-config）で対応できる。Manabrew が Forge を native-image に通しているので、その設定が参考になる。
